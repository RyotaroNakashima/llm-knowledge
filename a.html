普段の業務と、LLM Wiki

普段は、LLM Wikiのあるワークスペースで仕事を進めています。

業務の中心

検証・調査
メンバーの管理

設計・実装・テストを一通り回す
大きな開発タスクは少なめ。

業務に合わせた選択

AI-DLCも軽く試したが、
自分のタスクには少し重かった。

普段はLLM Wikiと呼ばれるものを
中心に作業を進めています。

普段Kiroを使っているので、Kiroを例に説明します。

LLM Wikiとは：記録をつなぎ、仕事に使う

資料や作業記録をノートに整理し、リンクでつなぎ、
知識・作業情報・判断の経緯を後から引き出す仕組み。

一番のメリット：作業の再開コストが減る

記録から状況をつかみ、中断した仕事の続きに戻りやすい。

  • AIへ渡せる情報が増える
  • 覚えておく負担が減る

AI-DLCは要件・設計・実装・テストなどの開発工程に、
LLM Wikiは業務全般の情報の蓄積・再利用に軸を置く。併用もできる。

LLM Wikiが解決する課題：背景を何度も説明する負担

口頭の決定や会議の経緯、細かな作業情報は、
AIに渡せる形になっていないことがある。

そのため、AIに仕事を任せるたびに、
人が情報を探し、背景を説明し直している。

この説明を人が繰り返すことが、
AIを使って仕事を進める際のボトルネックになっている。

対処：全作業をLLM Wikiへ記録する

技術調査、SKYWIZの返信案、エラー調査、数値整理などを
基本的にすべてKiroで進め、LLM Wikiに記録する。

SKYWIZの会話、会議の発言、PowerPoint資料などは
MCPやファイルで取り込み、ほかの作業情報とつなぐ。
口頭での会話も、内容を入力して記録する。

こうして仕事の経緯を蓄積することで、
毎回説明し直さず、中断した作業もすぐに再開できる。

外部情報の補完：取り込み方を使い分ける

作業情報があるツールからは、方法を工夫して
重要な情報をできるだけ漏れなく取り込む。

会議はなるべく録画し、文字起こしをファイル化して取り込む。
PowerPoint・Excelは対応MCPで読み取って取り込む。

GitLab WikiはGit管理されているため、cloneして取り込む。

SKYWIZの会話やRedmineのチケットは、MCPで取り込む。
（この2つはタスクスケジューラーでの定期実行もおすすめ）

余談：Kiroに渡せない情報を扱うとき

SKYPCEの名刺情報などは、通常のKiroには投入できなかった。
そこでコーディングエージェントに社内ローカルLLMの
エンドポイントを接続して扱った。

テックリーディングの社内GPU（H100など）でLLMを稼働し、
VS CodeのGitHub CopilotのCustom Endpointに接続する。

チャットに加え、ファイル操作や情報の取り込みにも使える。

GPUと運用環境は必要ですが、要望があれば構築方法も共有できます。

LLM Wikiの活用例

蓄積した記録と外部情報への接続を活用することで、
曖昧な指示でも情報の検索・活用ができる。

「今日の日報を書いて」
作業記録とSKYWIZを参照し、日報スキルで下書きする。

「最近いじったレンタル品のファイルって、どこにあるっけ？」
新規チャットでも記録のリンクをたどり、パスを返す。

「今日のタスクを教えて。未更新のTODOも更新しといて」
未整理の記録・会話・チケットを照合して整理する。

「SKYWIZで〇〇さんがこう言ってるけど、よく分からない。説明して」
作業記録と会話から、話題のつながりや背景を説明する。

運用方針：全案件をひとつのLLM Wikiへ

文脈が混ざらないよう、案件ごとにワークスペースを分ける使い方がある。
その場合、案件を変えるたびに作業場所や設定も切り替わる。

私はひとつのワークスペースのLLM Wikiに全情報を集約し、
切り替えずに使っている。

案件をまたぐ知見や共通設定も同じ場所で扱えるため、管理が楽になる。

目次・リンクと入口の情報量を工夫し、約半年分を大きな混乱なく運用。
（大規模な開発を担当する機会は少ない）

ワークスペースの構成

ワークスペース/
├ README.md
├ index.md
├ skills/LLM Wiki.md
└ プロジェクト/
   ├ 案件A/
   │ ├ index.md
   │ ├ 情報源/
   │ ├ ノート/
   │ └ 作業記録/
   └ 案件B/ …

情報は案件ごとに整理し、
目次から必要な記録へ進む。

情報源・ノート・作業記録をリンクし、
関連する作業記録同士もつなぐ。

次のチャットでもリンクをたどって、
過去の経緯を引き出せる。

Obsidianでは、記録間のリンクを関係グラフで確認できる。

課題：ルートの目次が肥大化する

作業記録をルートの目次に並べ続けると、
目次が大きくなり、毎回読み込む情報が増えてしまう。

そこで目次を階層化し、まず対象の案件を絞る。
ルートのindex.mdには、各案件の概要とキーワードを置く。

たとえば「名刺」「OCR」「学習」を手がかりに、該当する案件へ進む。
案件ごとのindex.mdには、作業記録・ノート・情報源の目次を置く。

最初からすべての目次を読まず、必要な案件の情報だけを詳しく読む。

課題：作業記録でコンテキストが膨らむ

概要とコマンド・ログなどの詳細を一緒にすると、
状況確認だけでも、長い記録を読み込んでしまう。

そこで、概要・意図・結果・判断理由・TODOの要約と、
コマンド・エラーログ・生データの詳細を別ファイルに保存する。

目次からまず要約を読ませ、必要なときだけ詳細へ進む。
不要なログの読み込みが減り、扱いやすくなった。

読み込み方針：入口は薄く、必要なときに深く

全記録を最初から読ませず、問いに応じて読む範囲を広げる。

  1. まずルートの目次を読み、どの案件の話かを絞る。
  2. その案件の目次から、関係しそうな作業記録を探す。
  3. 記録の要約を読み、今回の問いとの関連を判断する。
  4. 深く関係する場合だけ、詳細記録でログや根拠を確認する。

よく読む目次・要約は情報量を絞り、
必要な内容へ正しく案内する質を高めることが重要だと考えている。

まとめ・ご紹介

作業記録と外部情報を集め、必要な範囲だけ読むことで、
説明し直す負担を減らす。
